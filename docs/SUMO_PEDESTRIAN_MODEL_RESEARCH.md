# How SUMO Represents Pedestrian Paths & Areas — a Research Report for the Graph/Drawing Spec

*Status: research, fact-based, verified against the current SUMO documentation
(July 2026). Audience: the OSM / drawing side defining our spec for pedestrian
**paths** and **areas**. Purpose: so that whatever we draw and put in the graph
maps cleanly onto something SUMO can actually simulate.*

*Scope note: this is about the **SUMO** target, not WebSUMO. It exists because our
intersection graphs already carry pedestrian data (269's `graph.ttl` has ~94
`Crossing` and ~113 `Zebra` nodes), but `graph2sumo` currently emits a
vehicle-only network and drops all of it. Before we formalise pedestrian paths
and areas in the spec, we should know what SUMO can consume.*

---

## TL;DR for the spec authors

1. **SUMO is fundamentally edge-based, even for pedestrians.** In the default
   model, pedestrians walk on **lanes** (sidewalks), **edges** (footpaths),
   and **crossings** (edges across a road). The only genuine 2D *surface* in a
   normal SUMO network is a **walkingArea**, and those are **auto-generated at
   junctions** — you don't usually hand-author them.

2. **Paths map cleanly; free-form areas do not.** A drawn pedestrian **path**
   (a polyline) maps naturally to a sidewalk lane or a footpath edge. A drawn
   pedestrian **area** (an arbitrary polygon — a plaza, a shared space) has **no
   first-class routable representation** in the default (`striping`) model. You
   either (a) decompose it into a mesh of footpath edges, (b) let it become a
   junction walkingArea, or (c) target the newer **JuPedSim** model, which *does*
   simulate continuous 2D areas but is young and has real limitations.

3. **Therefore the spec's key early decision is: what is a "pedestrian area" for
   us?** A routable open surface (→ JuPedSim or edge-mesh), a
   junction-connector (→ walkingArea, generated), or a purely visual polygon
   (→ not simulated). These have very different data requirements. Pick per
   feature; don't model all "areas" the same way.

4. **Crossings carry the most structured data** and are worth modelling
   explicitly: which road edges are crossed, the junction, whether signalised
   (and the signal-plan indices), width, and priority. This is exactly the data
   a SUMO `<crossing>` needs — and it's where the pedestrian↔signal↔V2X story
   lives.

## The three pedestrian models (this determines what "area" even means)

SUMO selects the pedestrian model with `--pedestrian.model` (default `striping`).
The choice matters to the spec because it changes what a pedestrian *is*.
[[Pedestrians]]

| Model | What a pedestrian is | Uses areas? | For us |
|---|---|---|---|
| `nonInteracting` | A point moving along its route at fixed speed; **no interaction** with anyone; "jumps" across intersections | No | Only for trivial throughput; not realistic |
| `striping` (**default**) | Confined to the pedestrian network (sidewalks + footpaths + crossings + walkingAreas); moves **longitudinally along edges** with **lateral "stripes"** to pass/oncoming | Only junction walkingAreas | The realistic-but-network-bound baseline |
| `jupedsim` | A **free agent in continuous 2D space**, real crowd dynamics (`CollisionFreeSpeedModel`) | **Yes — true walkable areas** | The "areas" answer, but young (see maturity) |

### `striping` in one paragraph (the default you'll be feeding)
The walkable width of a lane/crossing/walkingArea is divided into **stripes**,
default **0.65 m** wide (`--pedestrian.striping.stripe-width`). A pedestrian
occupies a stripe and moves forward like a vehicle along a lane, changing stripes
to overtake or dodge oncoming pedestrians. So it is **1-D along the edge + a
discretised lateral dimension** — *not* free 2D, and *not* a social-force model.
It models bidirectional flow, reserves ~1/3 of width for oncoming traffic at
junctions, and has jam-recovery timers (`--pedestrian.striping.jamtime` 300 s,
10 s on crossings). Practically: **a pedestrian's position is "edge + lateral
offset,"** which is why grounding a pedestrian to a lane/crossing IRI works much
like it does for vehicles. [[Pedestrians]]

## Q1 — Ways SUMO represents pedestrian paths and areas

There are **four network element types** plus **two kinds of "area."** All are
defined in plain-XML network input (`.edg.xml`, `.con.xml`) or generated by
`netconvert`. [[Pedestrians]] [[PlainXML]]

### Paths (linear)

- **Sidewalk** — "a lane which only permits the vClass *pedestrian*." Added to a
  road edge either as an explicit `<lane allow="pedestrian" width="…"/>` child,
  or via the edge attribute **`sidewalkWidth`** (default `-1` = none), or
  generated (see Q2). **Hard limit: at most one sidewalk per edge.**
- **Footpath** — a standalone **edge** that allows only pedestrians (a dedicated
  walkway with its own from/to nodes, not attached to a road). This is the
  natural target for a drawn pedestrian *path* that isn't a roadside sidewalk.

### Crossings (linear, but structured)

- **Crossing** — an edge letting pedestrians cross a road **at a junction**.
  Defined with `<crossing>` in the connections file. Attributes
  ([[PlainXML]]):
  - `node` (**required**) — the junction id the crossing belongs to
  - `edges` (**required**) — the road edge(s) being crossed
  - `priority` (bool) — pedestrian right-of-way; **auto-true at traffic lights**
  - `width` (m), `shape` (explicit geometry, counter-clockwise around the node)
  - `linkIndex` / `linkIndex2` (int) — **signal-plan indices** for the forward /
    backward direction (how the crossing ties into the TLS)
  - `discard` (bool) — remove a crossing
  - SUMO recognises three kinds: **priority (zebra)**, **unprioritised**, and
    **traffic-light-controlled**. [[Pedestrians]]

### Areas (2D)

- **WalkingArea** — the polygon at a junction that stitches sidewalks, footpaths
  and crossings together so pedestrians can move between them. **Auto-generated**
  when `--crossings.guess` is set or any crossing exists; can be *customised* (not
  usually authored) with `<walkingArea node="…" edges="…" shape="…" width="…"/>`.
  This is the **only 2D surface in a default network**, and it exists **only at
  junctions** — you cannot make an arbitrary mid-block plaza a walkingArea.
  [[Pedestrians]] [[PlainXML]]
- **JuPedSim walkable area** — with `--pedestrian.model jupedsim`, the walkable
  surface is a real closed polygon (with holes for obstacles), either **converted
  from the SUMO pedestrian network** or **drawn** (netedit / DXF import).
  Additional-file shape types: `jupedsim.walkable_area`, `jupedsim.obstacle`
  (holes: trees, pillars, stalls), `jupedsim.vanishing_area` (exits / capacity
  sinks), `jupedsim.influencer` (routing hints). **This is the only way SUMO
  simulates a genuine open pedestrian area.** [[Pedestrians]] [[JuPedSim]]

### Demand (who walks, and where)
Pedestrians are **persons**, not vehicles — a separate demand and API.
`<person>` / `<personFlow>` carry a plan of stages: `<walk>` (by `route`, `edges`,
or `from`/`to`, routed over the pedestrian network), `<ride>` (board a vehicle /
line), `<stop>`, and router-level `<personTrip>`. A person needs a vType with
**`vClass="pedestrian"`** (default `desiredMaxSpeed` 1.39 m/s). [[Persons]]
Runtime access is via `traci.person.*` — **distinct from `traci.vehicle.*`**
(this is why our adapter, which only reads `traci.vehicle`, sees no pedestrians).

## Q2 — How mature is each method?

| Method | Maturity | Notes |
|---|---|---|
| `striping` | **Mature / production** | The long-standing default; realistic enough for crossings, queues, bidirectional flow. Well documented, TraCI-controllable. |
| `nonInteracting` | Mature but trivial | No interactions; use only when dynamics don't matter. Incompatible with networks lacking pedestrian edges. |
| `jupedsim` | **Emerging / work-in-progress** | Integrated in **SUMO 1.19.0 (2023)**; extended in **1.20/1.21 (2024)** to wait at crossings. Real crowd dynamics, but see limitations below. [[ChangeLog-2023]] [[ChangeLog-2024]] |
| `netconvert` sidewalk/crossing **guessing** | Usable but heuristic | `--sidewalks.guess` (speed-band based), `--crossings.guess`, `--walkingareas`. Convenient but **frequently needs manual correction**. |
| **OSM import** of pedestrian infra | Usable, quality-variable | Two strategies with an explicit trade-off (below). |

### `striping` limitations to know
- **One sidewalk per edge** (a hard modelling assumption).
- If `stripe-width` < an agent's path width, **100 % collision safety is not
  guaranteed** on shared lanes.
- Not continuous 2D; open plazas / large squares are not representable as such.
  [[Pedestrians]]

### `jupedsim` limitations to know (important before betting "areas" on it)
- **Pedestrians do not react to vehicles yet** — "planned for future
  implementation"; cars treat pedestrians as obstacles. For a V2X /
  vehicle-pedestrian-conflict story this is a **big caveat today**.
- **Slow**: internal timestep ~**0.01 s**, described as "the runtime-limiting
  factor" of a coupled simulation.
- **Only one connected pedestrian network component** is kept (the largest).
- **Static waiting positions**; waiting-behaviour modelling is being refined.
- Only the `CollisionFreeSpeedModel` is extensively tested. [[JuPedSim]]

### OSM import trade-off (directly relevant to our source data)
- **Typemap approach** (`osmNetconvertPedestrians.typ.xml`): adds sidewalks to a
  chosen set of road types with preset widths → **good coverage, but risks
  duplicate/double sidewalks**.
- **`--osm.sidewalks`**: trusts explicit OSM sidewalk tags → **no duplicates, but
  missing sidewalks wherever OSM mappers didn't tag them**.
- **`--osm.crossings`**: generates crossings from `highway=crossing`. By default
  netconvert imports only dedicated footpaths unless these options are set.
  [[OSM-Import]]

## Q3 — What to take into account if we add pedestrian paths/areas to the graph

Framed as guidance for the spec. The recurring theme: **SUMO wants
edges + connectivity + (for crossings) signal linkage; it does not want free
polygons except under JuPedSim.**

### If we model pedestrian **paths**
- A roadside path → a **sidewalk on a road edge**: capture **width** and the fact
  that it belongs to a specific road edge/side. Remember **one sidewalk per
  edge** — don't spec left+right as two sidewalks on the same SUMO edge.
- A standalone path → a **footpath edge**: capture **from-node, to-node,
  polyline geometry, width**. Footpaths need real endpoints that connect into the
  junction/walkingArea graph, or pedestrians can't route on/off them.
- Sidewalks are **bidirectional** for pedestrians (one lane used both ways) —
  don't spec a direction per pedestrian path unless it's genuinely one-way.
- **Width is not cosmetic**: it sets stripe count → capacity in `striping`.
  Capture a real width, not a default.

### If we model **crossings** (highest value — do this well)
Capture exactly what a SUMO `<crossing>` needs, because it's structured and it's
the pedestrian↔signal bridge:
- the **junction** it belongs to;
- the **road edge(s)** it crosses;
- **signalisation**: is it TLS-controlled, and if so which **signal group / link
  index** (maps to `linkIndex` / `linkIndex2`) — this is the natural join to the
  same TLS data our vehicle connections already ground onto;
- **priority** (zebra vs unprioritised) and **width**;
- optionally explicit **shape** (SUMO expects counter-clockwise around the node).
- Our graph already has `Zebra` / `Crossing` nodes — the spec should make sure
  they carry *these* fields, not just geometry.

### If we model pedestrian **areas** — decide the semantics first
This is the crux. An arbitrary pedestrian polygon has **no routable form** in the
default model. For each "area" feature, the spec should classify it:
- **Junction connector** → it's really a **walkingArea**. Don't author the
  polygon; author the **connectivity** (which sidewalks/crossings meet here) and
  let `netconvert` generate it. Optionally carry a shape override.
- **Routable open surface** (plaza, shared space, station forecourt) → only
  **JuPedSim** can simulate it. Then the spec needs a **closed polygon +
  obstacle holes + entry/exit** (`walkable_area` / `obstacle` /
  `vanishing_area`), and we accept JuPedSim's cost/immaturity (and today, no
  vehicle reaction).
- **Decompose-to-edges** → if we want the default model, an area must be broken
  into a **mesh of footpath edges**; the spec would need a triangulation/skeleton
  step. Heavier, but stays in the mature model.
- **Visual only** → carry it as a polygon/shape with no routing; SUMO won't
  simulate movement on it.

### Cross-cutting
- **Connectivity is king.** SUMO builds walkingAreas from *how* sidewalks,
  footpaths and crossings connect at a node. Geometry without connectivity gives
  disconnected pedestrian islands. The spec must capture node membership and
  adjacency, not just shapes.
- **Keep the vehicle-network join.** Crossings reference road edges; ride/stop
  stages reference `busStop`/lanes. Pedestrian features should reference the same
  edge/junction ids the vehicle side already uses.
- **Coordinate/shape conventions**: crossing/walkingArea shapes are coordinate
  pair lists; crossings expect counter-clockwise ordering around the junction.
- **OSM provenance**: if features come from OSM, know which tags drove them
  (`sidewalk=both/left/right`, `footway=sidewalk/crossing`,
  `highway=footway/pedestrian/crossing`, `area=yes`) — coverage gaps in OSM
  become coverage gaps in the network.

## How this lands on our stack (context, not a task)
- Our graph already models pedestrian crossings/zebras richly; the gap is
  **graph2sumo**, which emits a vehicle-only network. Whatever the spec settles,
  graph2sumo will need to emit `<crossing>`, sidewalk lanes / footpath edges, and
  (if we go there) JuPedSim walkable-area additional files.
- Our **adapter reads only `traci.vehicle`** — pedestrians would also need
  `traci.person` support to appear in the viewer, the `sees`/LDM graphs, and any
  V2X/VRU story. Pedestrians are the vulnerable road users collective perception
  is really about, so under `striping` (edge + lateral offset) they'd ground and
  merge much like vehicles; under JuPedSim (free 2D) grounding becomes pure
  position→crossing map-matching — the same sim-vs-real seam we already designed.
